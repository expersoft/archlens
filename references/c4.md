# C4 no archlens

## Níveis

| Nível | Mostra | `scope` |
|---|---|---|
| `landscape` | todas as pessoas e sistemas de software | — |
| `context` | um sistema + pessoas e sistemas ligados a ele | softwareSystem |
| `container` | containers de um sistema (dentro do boundary) + externos ligados | softwareSystem |
| `component` | componentes de um container + containers irmãos e sistemas ligados | container |
| `dynamic` | passos numerados de uma interação | softwareSystem ou container |

## Hierarquia e ids

```
person                       (topo)
softwareSystem               (topo)
 └─ container                (filho de softwareSystem; tag "database" → cilindro)
     └─ component            (filho de container)
```

Na base (formato 2.0) isso é gravado como lista plana: cada elemento tem `parent` e `c4: { "kind": … }`
(`person`, `softwareSystem`, `container`, `component`, `deploymentNode`, `infrastructureNode`). Na entrada (delta,
prompt, `scan`) você pode escrever `c4:container` e `children`; a tradução faz o resto.

Use ids hierárquicos (`loja.pedidos.checkout`). Eles deixam o modelo legível e estável.

## Elevação e agregação

Relações são declaradas no nível mais preciso que se conhece (componente → container). Cada visão
as **eleva** ao nível que mostra: numa visão de containers, `loja.pedidos.checkout → gateway` aparece
como `API de Pedidos → Gateway`. Relações que caem no mesmo par viram uma seta só, com as descrições
e tecnologias unidas e a contagem guardada.

## Estilo

Cores padrão C4: pessoa `#0b3d78`, sistema `#1168bd`, container `#3f86d0`, componente `#8cc0f2`,
externo cinza. As setas são tracejadas, com descrição e `[tecnologia]`. O elemento em foco ganha borda
dourada. Elementos inferidos (de texto livre ou da leitura de repositórios) têm borda tracejada.

## Relação com ArchiMate

| C4 (entrada) | ArchiMate (gravado) |
|---|---|
| person | `business-actor` (ou `business-role`) + `c4.kind: person` |
| softwareSystem, container, component | `application-component` + o kind (hierarquia por `parent`) |
| container `database` | `application-component` + `c4.kind: container` + tag `database`; o conteúdo, quando conhecido, é `data-object` com `parent` no banco |
| `deploymentNode`, `infrastructureNode` | `node`, `device`, `system-software`, `technology-service` ou `communication-network` + o kind |
| `A uses B` | `B serving A` (o `uses` é consumidor → provedor, e `serving` aponta do provedor); `A access B` se B é dado (`accessType`, padrão `readwrite`) |

## C4 a partir de ArchiMate

Um modelo escrito só com tipos ArchiMate também gera setas C4. Os **intermediários** são `application-service`,
`application-interface`, `application-function` e `application-process`. O **dono** de um intermediário é todo elemento
com `c4.kind` que o **realiza** (`realization`), é **atribuído** a ele (`assignment`), o **compõe** (`composition`) ou é
o seu `parent`; o dono vale também através de outros intermediários. Exemplo: com `B realization S` e `S serving A`, a
visão mostra `A → B`. Com dois donos, saem duas setas; intermediário sem dono não gera seta.

- A seta **derivada** é tracejada e o tooltip diz "via <intermediário>". A descrição é a da relação original (ou o
  nome do intermediário). Se o par já tem seta direta, a derivada entra nela (contagem, descrições, tecnologias).
- `"derive": false` na visão desliga a derivação (padrão ligado).
- Um `data-object` com `parent` num container sobe até ele (`API → Banco de Pedidos`); sem `c4.kind`, ele nunca é
  desenhado como caixa C4.

Um mesmo container participa das visões C4 (como caixa azul) e das ArchiMate (como application
component). É isso que liga "quem chama quem" (C4) a "o que sustenta qual oferta" (ArchiMate).
